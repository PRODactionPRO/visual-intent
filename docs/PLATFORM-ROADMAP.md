# Платформенный roadmap

Этот roadmap описывает направление, а не уже выпущенную функциональность. Каждая фаза должна завершать полноценный пользовательский цикл до добавления следующей платформы.

Согласованные требования к будущим макетам панели собраны в [«Интерфейсном brief Visual Intent»](INTERFACE-BRIEF.md). Сводная приоритизация открытых инициатив и относительные оценки находятся в [«Бэклоге Visual Intent»](BACKLOG.md).

## Фаза 0 — локальный web proof (реализовано)

- TypeScript-monorepo с protocol, core, SDK и adapters.
- Loopback reverse proxy с инжектируемым overlay.
- Контекстный редактор Select/Draw, редактируемая очередь Tasks и явный пакетный Apply.
- Проектные сессии, привязанные к репозиторию, и надёжный статус Apply-пакетов.
- Git-baseline, отдельный учёт старых dirty-файлов и изменений конкретного Apply; default `allow-host-attached` без дублирующего подтверждения и опциональный `require-confirmation`.
- Автопривязка задачи Codex из MCP-метаданных или переменных с безопасным явным fallback без угадывания активной задачи.
- Безопасный по умолчанию режим `disconnected`, handoff подключённой задаче через MCP и отдельный, явно включаемый Codex SDK worker.
- Исходники Codex-плагина с hook `SessionStart`, проектным skill и MCP-инструментами на базе daemon.
- Файловое JSON-хранилище, защищённые токеном операции изменения и WebSocket, MCP-мост через stdio.
- Пример на React/Vite и автоматические проверки.

Критерий завершения: команда использует зафиксированные задачи в реальном локальном проекте и понимает, какой недостающий контекст приводит к повторной работе агента.

### Закрытая обратная связь локального цикла — 2026-08-18

- **VI-001 — resolved:** плагин получает ID текущей задачи из MCP-метаданных, `CODEX_THREAD_ID` или `CODEX_SESSION_ID`; явный `threadId` остаётся безопасным fallback. Проверено реальным MCP-подключением к proxy без переменных окружения.
- **VI-002 — resolved:** daemon сохраняет Git-baseline при Apply/claim и после finish отделяет `batchChangedFiles` от `preExistingDirtyFiles`. Проверено автоматическими тестами с изменением старого dirty-файла и созданием нового.
- **VI-003 — resolved:** проектная настройка выбирает поведение dirty-worktree. Для связанного `host-attached` чата рекомендуемый режим сохраняет baseline и передаёт пакет без дублирующего подтверждения; режим «Спрашивать подтверждение» и автономный worker сохраняют точную fingerprint-защиту. Настройка хранится daemon с ревизией, а не в браузере.

### Измерительный контур ценности — текущий MVP-срез 2026-08-24

- Первоначальная задача и последующие уточнения образуют одну итерацию; `needs_revision` создаёт следующий раунд, а технический retry увеличивает попытку того же Apply-пакета.
- Tasks разделён на Backlog, In progress и Ready. Якоря существуют только у текущего Backlog и скрываются сразу после Apply. In progress и Ready группируются по свёрнутым пакетам; самый новый неоценённый Ready-пакет может один раз раскрыться для запроса обратной связи, а оценённые карточки приглушаются.
- Workflow-решения `accepted`, `needs_revision` и `not_accepted` остаются отдельным контрактом; только `needs_revision` создаёт следующий раунд, а отрицательная оценка не запускает скрытый откат файлов.
- Агент сам присваивает задачам мультиметочные категории и масштаб, не заставляя пользователя заполнять аналитические поля.
- Каждая завершённая попытка получает локальную append-only execution-запись, а жизненный цикл — privacy-safe event-записи без текста комментариев, DOM и изображений.
- Exact token usage хранится только на уровне всего agent turn Apply-пакета. Для SDK worker он читается напрямую; для host-attached режима отсутствие доверенного receipt честно отмечается как `unavailable`.
- Проектная задача Codex хранится отдельно как controller и не заменяет автономный executor. Постоянная запись `sdkWorker` хранит другой SDK thread с первого события запуска и возобновляет его между Apply и перезапусками proxy; autonomous thread не равен controller.
- Каждый Apply фиксирует собственный снимок `.visual-intent/context.md`; позднейшее редактирование briefing не меняет уже отправленный пакет.
- Один проект допускает только один proxy-daemon и один активный SDK worker: отдельные атомарные project lease блокируют второй процесс. Worker lease после мёртвого PID не восстанавливается автоматически, потому что дочерний Codex-процесс мог пережить daemon; recovery требует явного флага после проверки процессов и diff. После подтверждённого аварийного обрыва частичный diff сохраняется, пакет становится retryable `worker_interrupted`, а откат и повтор остаются явными действиями.
- Host-attached claim выдаёт receipt из `claimId`, `attempt` и controller thread; finish отклоняет чужую или устаревшую попытку. Автоматическое восстановление прерванного host-attached claim пока не реализовано, потому что daemon не владеет внешней задачей Codex.
- Обычный `needs_input` принимает ответ, увеличивает attempt и возвращает в очередь только нерешённые задачи; уже выполненные части не запускаются повторно.
- API и MCP принимают `direct` usage и claim/finish только по доверенному маршруту: автономным пакетом владеет daemon, host-attached пакет завершает подключённый агент.
- Команда `visual-intent metrics` агрегирует задачи, пакеты и оценки из `tasks.json` вместе с events/executions из `usage/` в table, JSON или CSV без cloud analytics.
- Команда `visual-intent reset --repo <path> --yes` безопасно начинает новую локальную выборку: удаляет историю и attachments выбранного проекта, сохраняет сессию, настройки, подключение и context и блокируется при активном Apply-пакете.

Первый исследовательский режим: проводить часть Apply с одной задачей разных категорий и масштаба, а часть — пакетами разного размера. Так single-task запуски дадут точные сравнимые точки, а пакетные покажут практический эффект группировки без искусственного распределения токенов.

Критерий завершения среза: на внутренних проектах воспроизводимо считаются время до принятия, first-pass success, дополнительные раунды, usage coverage, точные batch tokens, наблюдаемые операции и guardrails; ни один недоступный показатель не заменяется оценкой.

## Фаза 1 — полезный цикл web-разработки

- Framework-aware подсказки исходников для React и распространённых web-стеков без добавления React в core.
- Надёжный Select при прокрутке, responsive layout, iframe и shadow roots.
- Скриншоты и метаданные viewport с явным контролем приватности согласно дискуссионному документу [«Будущая работа с медиа, хранением и стоимостью»](FUTURE-MEDIA-AND-USAGE.md).
- Проектные квоты локальных медиа, предварительный просмотр очистки и retention controls до внедрения генерации изображений.
- Уточнение задач, история итераций, пользовательская оценка результата и повторное открытие.
- Шаблоны агентного workflow, требующие preview, проверки репозитория, верификации и отчёта о результате.
- Понятные статусы и история в браузере: connected, running, needs-input, completed и failed.
- Упакованный процесс установки и обновления Codex-плагина.
- Упакованный CLI и исследовательский browser extension; основной adapter выбирается по результатам наблюдений.

Критерий завершения: повторное использование в нескольких внутренних репозиториях требует существенно меньше уточнений, чем обмен скриншотами и сообщениями в чате.

### Согласованное локальное направление — Chrome Extension и Figma plugin

До публичного распространения Visual Intent должен получить два локально устанавливаемых adapter-модуля для собственных рабочих сценариев:

- распакованное расширение Chrome в режиме разработчика, которое умеет на любом обычном сайте выбрать DOM-элемент, собрать ограниченные HTML/computed-style данные и принять сделанные пользователем изображения через upload, drag-and-drop или paste;
- локальный development plugin Figma, который принимает подготовленный reference package и создаёт из него редактируемые слои в явно выбранном Figma-файле;
- общий локальный handoff через daemon Visual Intent: расширение и Figma plugin не связываются друг с другом скрытым глобальным состоянием, а обмениваются непрозрачным ID пакета через контролируемый localhost API;
- два явных назначения одного capture: добавить референс в контекст coding-агента либо импортировать визуальную структуру в Figma;
- проектная привязка применяется только по явному выбору пользователя. Референс с произвольного внешнего сайта сначала является локальным черновиком и не попадает автоматически в репозиторий продукта.

Первая реализация предназначена только для личной локальной работы: Chrome Extension загружается через `chrome://extensions` как unpacked extension, Figma plugin — из manifest как development plugin. Публикация в Chrome Web Store или Figma Community, облачный backend, аккаунты организации, auth, биллинг и юридическая подготовка сейчас не входят в план. Актуальные требования площадок должны быть заново проверены непосредственно перед решением о публичном релизе.

Для локального сценария backend не требуется: daemon, файловый transport и локальное хранилище достаточны. Архитектура при этом сразу сохраняет заменяемый transport, чтобы будущий collaboration backend мог добавить синхронизацию, не меняя формат reference package и логику adapters.

Первая реализация `VI-CHROME-001` сознательно не скачивает JavaScript и stylesheet-файлы и не реализует собственный screenshot capture. Для основной задачи визуального референса достаточно текущей HTML-структуры, allowlist computed CSS и системного снимка, который пользователь при необходимости вставляет в composer. Поведение компонента пользователь описывает агенту отдельно.

## Фаза 2 — основа connector plugins

- Публичный connector SDK, manifest возможностей, schema конфигурации, контракт идемпотентности и conformance tests.
- Исходящие направления задач для Jira, Яндекс Трекера и Notion.
- Agent adapters для MCP-инструментов, Codex, Claude Code, Cursor и других совместимых клиентов.
- Preview доставки и явное подтверждение до создания внешней задачи.
- External IDs, состояние повторов, dead-letter handling и безопасное хранение секретов.

Критерий завершения: одну задачу можно осознанно направить двум различным providers без утечки provider-логики в core.

Image-generation provider рассматривается как возможный connector после проверки скриншотов, безопасного жизненного цикла медиа, измерения стоимости и явного подтверждения. Он должен оставаться необязательным и тарифицироваться отдельно.

### Согласованное продуктовое направление — Figma-задачи и будущий round-trip

**VI-FIGMA-001 — перенос выбранного компонента из работающего приложения в Figma.** Статус: поведение Figma-задачи согласовано для интерфейса; обратный перенос из Figma в код остаётся будущей фазой.

На панели Visual Intent нужна отдельная нативная команда, которая использует тот же принцип выбора, что и Select. Пользователь выделяет компонент работающего интерфейса и при необходимости добавляет короткий комментарий. Создаётся обычный черновик задачи вида `figma`, отмеченный иконкой Figma. Он ждёт общего Apply и отправляется связанному агенту вместе с остальными задачами текущей итерации.

Ожидаемый результат:

- к задаче автоматически добавляется универсальная инструкция создать выбранный компонент в Figma пиксельно точно в его текущем видимом состоянии, как он есть;
- без отдельной просьбы агент не придумывает дополнительные состояния и варианты и не усложняет результат выделением внутренних частей в самостоятельный набор компонентов;
- пользовательский комментарий дополняет базовую инструкцию и может явно запросить оговорки по стилю, исправления или несколько состояний;
- результат создаётся в явно прикреплённом к проекту Figma-файле и не может случайно попасть в другой файл или проект;
- Visual Intent сохраняет связь между репозиторием, исходным компонентом, задачей, Figma-файлом и созданным Figma node;
- Apply служит явным подтверждением отправки Figma-задачи наряду с остальными задачами пакета;
- компонент можно доработать в Figma, а затем будущей отдельной подтверждаемой командой вернуть согласованные изменения в кодовый репозиторий;
- Pixel Perfect проверяется не только визуально, но и сравнением screenshot/render, computed styles и доступной структуры компонента с явным отчётом о неподдержанных свойствах.

До реализации Figma connector и будущего обратного переноса необходимо отдельно определить источник истины и правила конфликтов между кодом и Figma, способ проектной привязки и авторизации Figma, представление responsive-вариантов и интерактивных состояний, работу со шрифтами и ассетами, а также границу между автоматическим переносом и ручной дизайнерской доработкой.

## Фаза 3 — collaboration backend

- Hosted projects, review sessions, командные роли и истекающий доступ внешнего клиента.
- PostgreSQL-хранилище задач и истории и object storage для управляемых медиа.
- Совместная работа в реальном времени, уведомления, назначение ревью и workflow разрешения комментариев.
- Браузерное расширение, подключённое к аутентифицированной среде ревью.
- API и webhooks для студий и внутренних продуктовых команд.

Критерий завершения: студия может пригласить клиента, собрать обратную связь к review build, обработать её и направить согласованную работу с доступной для аудита историей.

Это первая фаза, которой нужны облачный backend и аутентификация. Она не должна создавать зависимость локального open-source цикла от hosted-продукта.

## Фаза 4 — React Native adapter

- Development-only пакет `@visual-intent/react-native`, подключённый к приложению и локальному daemon; Metro доставляет JavaScript, но не становится хранилищем задач или доверенной границей проекта.
- Ссылки на иерархию компонентов и props, когда они доступны в runtime.
- Touch selection, in-app screenshot, рисование, комментарий, Tasks и Apply на эмуляторах и физических устройствах iOS и Android.
- Нормализация координат для density, safe areas, orientation и scroll containers.
- Автоматический контекст route, версии приложения и сборки, платформы, устройства и доступного component hint без передачи пользовательских данных приложения по умолчанию.
- Системный screenshot через iOS Share Extension остаётся fallback для карты, камеры, видео, Metal и других native surfaces, которые нельзя гарантированно снять через view capture.
- Интеграция всегда отключена в production-сборке, если отдельная конфигурация явно не разрешила внутреннее тестирование.

Критерий завершения: задача, зафиксированная в React Native на физическом iPhone, создаёт тот же конверт протокола и агентный workflow, что и web-задача, хранится в `.visual-intent/` правильного репозитория и после Apply попадает только в связанную проектную задачу Codex.

## Фаза 5 — native iOS adapter

- Swift package `VisualIntentKit` для development-сборок SwiftUI и UIKit с in-app composer, разметкой и явным Apply.
- Отображение view/accessibility hierarchy в `Node`.
- Overlay для симулятора и физического iPhone и локальный bridge transport.
- Source hints там, где metadata Xcode/runtime безопасно позволяют их получить.
- Development-only Share Extension принимает системный скриншот, уже размеченный штатными средствами iOS, и позволяет добавить комментарий почти по тому же сценарию, что feedback в TestFlight.
- App Group outbox временно сохраняет отчёт при недоступном Mac и удаляет локальную копию после подтверждённой доставки.
- Первый canary-потребитель — VeoX, где уже есть SwiftUI, Share Extension и App Group; после проверки общий iOS transport переиспользуется React Native adapter в ТОКБЕРИ.

Критерий завершения: Swift-инструменты на физическом iPhone могут принять in-app или системный screenshot, комментарий и контекст экрана, безопасно доставить их в правильный локальный проект и воспроизвести visual intent без встраивания TypeScript в runtime приложения.

### Общий mobile bridge для React Native и iOS

**VI-MOBILE-001 — локальный TestFlight-подобный цикл на физическом iPhone.** Статус: `planned`, дата фиксации: 2026-08-18.

- Текущий loopback daemon не открывается в локальную сеть напрямую. Отдельный opt-in mobile endpoint использует одноразовое pairing через QR-код или короткий код, отдельный истекающий токен и явный project/session ID.
- Bonjour может обнаруживать доступный Mac, но приложение запрашивает системное разрешение Local Network и объясняет назначение доступа. Отказ не ломает приложение и оставляет ручное подключение.
- Xcode и Metro отвечают за установку, отладку и доставку кода, но не являются каноническим transport или task store Visual Intent.
- Один iPhone может быть связан с несколькими проектами, но каждый отчёт имеет одного явно выбранного получателя. Daemon повторно проверяет репозиторий и связанную задачу Codex.
- После доставки бинарные файлы находятся только в `.visual-intent/media/` целевого репозитория, исключены из Git и подчиняются общим квотам, preview очистки и retention.
- Локальный сценарий не требует облачного backend. Backend понадобится только для удалённых тестировщиков, работы вне общей сети и управляемой командной истории.
- Событие iOS о создании системного screenshot не содержит само изображение. Поэтому основной надёжный путь — явный in-app capture либо системное действие **Поделиться → Visual Intent**.

## Фаза 6 — native Android adapter

- Kotlin library для Jetpack Compose и Android Views в development-сборках.
- Отображение semantics/layout hierarchy, density-aware координаты и emulator overlay.
- Development-only интеграция Gradle и локальный bridge transport.

Критерий завершения: Android captures проходят тот же набор conformance tests протокола, что и web, React Native и iOS.

## Фаза 7 — enterprise-продукт

- SSO/SCIM, детальные роли, policies и approval controls.
- Экспорт аудита, retention/legal hold, региональное развёртывание и private networking.
- Управляемый каталог connectors, observability, обязательства по уровню сервиса и поддержка.
- On-premise или private-cloud control plane после подтверждения спроса клиентов.

Enterprise-функции — платные расширения для координации, governance и эксплуатации. Протокол и полезный локальный workflow остаются открытыми.

## Межплатформенный критерий приёмки

Каждый новый adapter должен:

1. создавать текущую версию протокола и проходить общие fixtures;
2. отображать platform-native понятия в общие сущности без изменения core;
3. по умолчанию отключать capture в production-сборках;
4. документировать permissions, раскрытие приватных данных и влияние на производительность;
5. включать пример приложения и end-to-end тест локального создания задачи;
6. доказывать совместимость хотя бы с одним существующим MCP-потребителем.
